3. COMMUNICATION
In MEX, two processes may communicate with
each other using the two C o m m u n i c a t i o n
Primitives (CPs), OFFER and ACCEPT. A third CP,
WAITUNTIL, is used to support timeouts and will
be dealt with in §4.
Communication between two processes happens
through an intermediary object called a gate. For
communication to take place, one process must
offer data to a gate and a second process must
accept the data from the same gate. This
c o m m u n i c a t i o n is s y n c h r o n o u s , (i.e. once a
process offers data to a gate, it will become
blocked until another process accepts the data
and vice versa).

The fact that communication is synchronous
means that a process runs the risk of becoming
blocked each time that it tries to communicate.
This makes the programming of processes that
communicate
with
several other processes
difficult and prone to deadlock.
To resolve this problem, the construct S E L E C T
has been added to MEX. It allows a process to
attempt multiple CPs simultaneously. Consider
the example code in listing 1, here, a process tries
two CPs simultaneously. The whole select block
will become blocked until one of the CPs
synchronizes with another process, at which time
the code following the CP will be executed and
then the select block will be exited. The symbol
' [ ] ' is called the fat-bar and means 'or'. Note that
only one synchronization happens per select, once
one CP synchronizes, the others are retracted.

If two or more processes offer data to the same
gate while there are no accepts pending, then all
the offering processes will become blocked. When
a process then accepts data from that gate, it will
synchronize with one and only one of the
pending processes, the choice of which is based
on a FIFO queue. Again, the reverse case is also
true.
Readers familiar with ADA may notice strong
similarities
regarding
inter-process
communication, however there is one important
difference, communication in MEX is symmetric,
in ADA it is not. For more information on the
topic see [Riese89].

4.1 INTRODUCTION
A Wide Area Network is a large scale computer
network. Typically, it will encompass a country, a
continent or even the entire world. It consists of
many computers, interconnected in a variety of
different manners, such as modem links, satellite
links etc. The structure of the network is usually
more or less random, links being added as the
need arises. The network is usually not fully
connected, i.e. a computer in the network is not
directly connected to all the other computers. An
example of a W A N is given in figure 3.

Here, a select has been used to avoid a potential
deadlock. If, for example, each process simply did
an offer followed by an accept, the system would
deadlock, both instances of the process blocked in
the offer. The while loop forces the select to occur
two times, once for each CP, the guards prevent
the same CP from synchronizing more than once.
Another point of interest is the use of two gates,
if only one gate is used, then a process risks
synchronizing with itself.

4.3 PURPOSE OF SIMULATION
The purpose of this project is to study layer 3,
the Network layer. The function of this layer is
two fold, Routing and Flow Control. This project is
primarily concerned with the former, routing.
If, in figure 3, node A needs to send a packet to
node G, it must pass it through intermediary
nodes, for example using the route (A,D,F,G). It is
also possible to follow the route (A,B,D,F,H,G). The
decision regarding which route to follow is made
at the Network layer. Many different factors can
i n f l u e n c e the decision, for example queue
lengths, line speeds, estimated delay, etc. The
choice of routing algorithm can have an
e n o r m o u s effect on the overall network
performance.
Several different classes of algorithms have
been developed in response to this problem. This
simulator allows us to try these
and new
algorithms under different simulated conditions
and compare their efficiency.

5. ADVANTAGES OF MEX
There exist many languages that support
discrete event simulation. However, most of
these languages are poor in their support for
software engineering concepts. Modula-2, and
therefore MEX, is strong in its support of these
c o n s t r u c t s , they i n c l u d e m o d u l a r i t y , type
constructs, type abstraction, coroutines, and
separate compilation. The use of Modula-2 as a
simulation language is discussed in [Sharma88].

OC)NCLUSION
Although MEX was originally designed to
support the development of distributed systems,
and more specifically data c o m m u n i c a t i o n
protocols, we believe that the virtual time mode
combined with the strong support for software
e n g i n e e r i n g concepts present in Modula-2,
makes MEX a powerful tool for general discrete
event simulation.
