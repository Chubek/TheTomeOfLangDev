SUlMlMARY
Self-compiling compilers are compilers written in the programming language they are made
to compile. They constitute a very interesting case of portable programs, and are rapidly
gaining in popularity. This paper is an attempt to classify and evaluate the different methods
which have been used for writing and transporting such compilers, according to numerous
and various criteria. The potential implementor is then given an idea of the important factors
to be considered when selecting one of the many implementation methods available. The
study is centred around a specific case, the programming language Pascal and its many
compilers.

SELF-COMPILATION AND PORTABILITY

Portability
According to Reference 31, ‘portability is a measure of the ease with which a program
can be transferred from one environment to another’. More specifically, this measure can be
quantitatively evaluated as, for example, the ratio of the transportation effort upon the
initial implementation effort (a figure near zero characterizes a high portability), or better
yet, as the difference between one and this ratio, i.e. (1-T)/1.l9Thus, a program is 100
per cent portable if its transportation effort is nil, 80 per cent if its transportation effort is
20 per cent of its implementation effort, etc.
The definition given above is probably not sufficient, since it implies that any transportation with a portability greater than zero is useful. This is true only if the efficiency and
reliability of the transported system are not reduced, otherwise one could, for example,
use any succession of simulations and interpretations for transporting programs from one
computer to another, whatever be the inefficiency of the result. Consequently, we add to the
preceding definition: ‘portability is a measure of the ease with which a program can be
transferred from one environment to another, without any loss of those characteristics which
make its transfer desirable’.
The boundary between a useful transportation and a useless one is thus probably about
50 per cent. Below this figure, the transportation effort has been comparatively so high that
the transported product has every chance of being unreliable and inefficient.

Self-compilation
A self-compiling compiler is a compiler which can compile itself. This implies that it be
written in the language it compiles, and consequently that its size and complexity lie within
the bounds it has set for the program it is to compile.
The first requirement means that the compiled language must suffice for writing the
compiler. The tools which are really required for this purpose are not easy to enumerate,
especially because many programmers, and particularly compiler implementors, make a
habit out of using a language for applications it was not designed for. It is very easy, in many
languages, to mimic the existence of some missing features, by (mis)using present but
completely different ones. For example, the ability to manipulate characters seems to be a
must for a language used to write a compiler, but compilers have been written in Fortran,
which (for the present) completely lacks such facilities. On the contrary, some authors ask
for certain features which are completely unused by many compilers, for example the
concatenation of strings. We will limit ourselves in the present paper to languages with
which the construction of a compiler becomes a natural and relatively easy task.
The second requirement for self-compilation, viz. upon size and complexity, is a difficult
problem of balance. Consider the following extreme cases; if the language is very simple,
its compiler is small, but it cannot be written with the language. If the language is big and
powerful, its compiler may be so huge that it cannot handle such a big program as itself.
If the compiIer does not attempt to generate a good code, it will be small, but the generated
compiler will be inefficient, and maybe too large. If the compiler uses extensive optimization
techniques, it should produce high-quality code, but its usefulness has chances of being
encumbered by its size. The solution is to make a very difficult and critical compromise
between simplicity and power, for both the language and its compiler.43

Motivations
What are the reasons for writing a compiler in the language it compiles ? The first one is
simply that a high-level language is much better than a low-level one for writing such a
program. Using high-level languages for writing application programs is a widely accepted
practice, but their appropriateness in the programming of system programs is still being
debated. Compilers constitute the class of system programs for which the use of high-level
languages is most accepted. T o try and explain such a preference, one might say that:
when planning to write a compiler, it seems a good idea to use a high-level language; if the
language to be compiled is convenient, it seems a still better idea to use it, so only one
language will be involved in the whole.
When the preceding considerations are acknowledged, the implementor discovers a
completely new situation: since no other language is used than the one which is compiled,
no other compiler or assembler is needed, and the new system is completely self-contained
(if it is a pure compiler, but see also Pascal-P in the subsection Inventory of the cases
considered for a case which uses an interpreter). Implementing the language on a new
computer does not depend on any other processor or language, and this leads to the idea
of a portable compiler, which in itself is a very good way to favour the portability of other
programs. Nevertheless, even a self-compiling compiler has a point of origin. A method
known as bootstrapping is usually used to get things started. We will therefore devote the
central part of our paper to a discussion of the various adaptations of the method.

Examples
One of the first examples of self-translating translators which may come to mind is the
usual assembler. This is both a good and a poor example, since an assembler is impossible

to transport because of its sheer nature, v i z . its machine dependency. Another point is that
an assembler may be first written as a very simple program, using but one of the many
facilities it will implement, symbolic addresses. However, some of the methods which will
be considered in the section Pascal and its implementation are equally applicable to assemblers.
Historically, one of the first interesting and meaningful self-compiling compilers is the
one which was designed for the programming language Neliac,13 and which also helped in
the development of the language itself. The first step of the adopted method consisted in
the construction, in assembly language, of a kernel-compiler for a very small subset of the
intended language, barely sufficient for writing its own compiler. After that, successive
extensions to the language were implemented by accompanying successive expansions of the
compiler, each one compilable by its predecessor, i.e. written in a subset of the language
acceptable to the preceding compiler, and making full usage of this subset. This scheme
does not work very well for present-day languages, since most of them more or less conform
to the principles of orthogonal design, and a sufficiently small kernel language is very difficult
to define, and generally unusable for writing its own compiler.
Other interesting examples may be briefly quoted here, since our case study will encompass
all the different methods they used.
-Jovial36 compilers have been developed by using a common intermediate language. The
translator used to produce intermediate code from Jovial is machine-independent and
written in Jovial, while the translator responsible for generating machine code from
intermediate code is written anew for each machine, in its assembly language.
-XPL24 is compiled using a compiler-generator written in XPL. T h e bootstrap was made
by writing the first system in Burroughs extended Algol, then discarding this first version
as soon as the compiler-generator was able to generate a compiler for itself. The presence
of this generator has nothing to do with self-compiling, it is only a tool for automating a
part of the production of the compiler.
-The level H Fortran compiler for the IBM 36022 was written in Fortran, but it was
compiled by a lower-level compiler. Self-compilation was probably never attempted and,
furthermore, the Fortran version of the compiler was translated by hand into assembly
language, and then discarded. The experiment may well be considered a failure in this
respect.
-Other interesting cases worth mentioning are BCPL33 (using an intermediate languge),
EPLlO (rewritten in itself as an afterthought), Lisp25 (the compiler, written only in
Lisp, was compiled by its own interpreted incarnation), Sue,5 L I S 5 and Bliss.44 There
also exists an important number of so-called cross-compilers, where a compiler for language
L is written in L but runs on machine A and produces code for machine B (generally a
mini- or microprocessor). These are not self-compilable, and do not directly concern us
here.
PASCAL AND ITS IMPLEMENTATION

Our case study
The subject matter of our case study is made up of the various compilers designed for the
programming language Pascal.17 We chose this particular language because we are
extensively involved in its use for teaching programming18 and for writing (portable)
software20i21but also because it seems to be a very good example of the variety of means
which can be used for implementing a programming language.

Three qualities of Pascal make it a very good subject for self-compilation: it is a machineindependent language, much more that Fortran, PL/I or Bliss; it is a powerful language,
much more than Fortran or Algol 60, i.e. it contains powerful concepts such as records, files,
sets, pointers, case statement and so on; it is a simple language, much more than PL/I
or Algol 68, i.e. its compiler does not necessarily have to be a huge and multiphase program.
Historically, the construction of a Pascal compiler was first attempted by using Fortran
on the CDC 6000.41 It was already planned to have a self-compiling compiler, but Fortran
was expected to be a better implementation tool than machine language. I n fact, the
complete lack of any practical facility for writing system programs in this language made it
impossible to write an understandable and usable compiler, so it was discarded. The initial
bootstrap was consequently made in an uncommon way: first, a compiler for 60 per cent
of the language was written entirely in Pascal, then translated by hand into Scallop, a
medium-level programming language for the CDC 6000. The resulting enormous and
untested program served as a basis for the compilation of the compiler, and was discarded
as soon as it worked.
Subsequent compilers used the half-bootstrap method (see the subsection Distinguishing
Characteristics); the existing compiler, written in Pascal, and modified by hand to produce
code for a machine other than the CDC 6000, is compiled by the old compiler, giving a
CDC program able to produce code for another machine. The source of the modified
compiler is then given as data to the CDC program, resulting in the generation of the desired
compiler. This scheme has been used for the I C L 1900,40 IBM 360,14 CII 10O7Oz3and
Xerox Sigma* machine series. Completely new methods, simpler to use than the preceding
one, have been developed since then and have been used in the production of many other
compilers.

T H E ALTERNATIVE METHODS AND THEIR APPRAISAL

Distinguishing characteristics
The preceding list of cases, which does not cover all experiments in portability of selfcompiling Pascal compilers, only consists of well-known and well-described cases (P-6000-1
and 2, P-1900-1, Pascal-P, P-PDP-10) or of interesting cases we happened to know about
(Pascal-E, P-Sigma, P-Iris-50). Nevertheless, it gives a good sample of the different factors
of importance, and it will be the basis of our classification and evaluation.
The difficulty in defining a rigorous and hierarchical classification will be quickly evident,
since a first distinction according to the bootstrap method makes it difficult to take into
account other characteristics like the languages involved, for example, which in practice
bear a significant importance. We cannot, therefore, obtain an aesthetic tree classification.

Bootstrap method
Since the goal is to obtain a self-compiling compiler, the implementation method is
necessarily a bootstrap. We will distinguish between half-bootstraps, full bootstraps and
incomplete bootstraps.
According to Reference 37, a half-bootstrap is an implementation made on machine Y
(the target machine) with tools available on machine X (the source machine), as in Figure 14.
This method is used by P-1900, P-2900, P-Iris-80 and P-Sigma. Although P-Iris-50 has a
two-pass scheme, we will include it in this category.

Again according to Reference 37, a full bootstrap is an implementation where all work is
done on the target machine. Three methods may be considered for achieving this goal.
-Divide the compiler into two different parts, the first one generating an intermediate code,
translated by the second one; this is the method used for Jovial and Pascal-J. I n the latter
case, Janus may be implemented on any machine with Stage2 or another macroprocessor.
-First write the compiler in a high-level language for which a compiler is available on the
target machine, for example Fortran, PL/I, Algol W, XPL, then rewrite it in Pascal for
self-compiling it on the target machine. However, if the writing language is satisfactory,
the second step does not seem useful, and the produced compiler is not self-compilable.
Moreover, the compiler may be first written in Pascal, then translated by hand into the
implementation language, which serves only as a temporary tool. Three compilers on the
IBM 360-370 series exhibit these three different cases: the one from the University of
Manitoba3* was written only in PL/360; the one from SUNY at Stony Brookz9 was
written in XPL, then translated into Pascal; the one from Stanford University, called
here P-360, was first written in Pascal, and uses PL/I as a temporary tool, thrown out as
soon as possible because of its extremely poor performances.
-First write the compiler in its own source language, if a first compiler is available on the
target machine. This supposes that this first compiler is unsatisfactory, but able to compile
the second one. P-6000-2, P-1900-2, P-PDP-10 and P-Hitac-8000 fall in this category,

Other characteristics
Some important aspects of the preceding classification may be criticized. For example,
it does not suffice to distinguish clearly between particular implementations and general
methods. An implementation method is the use of either Pascal-J, Pascal-P, Pascal-E or a
trunk compiler, i.e. the use of an original compiler which allows different implementations.
These implementations will be made by bootstrap (since all these compilers are written in
Pascal), but not necessarily in the same way: Pascal-J necessitates Stage2 or another
macroprocessor, while Pascal-E may use Stage2 or a real translator, and a trunk compiler
may be used in a half or in a full bootstrap. On the contrary, P-1900 or P-Iris-80 are
particular constructs, made for a particular computer.
We can now enumerate and discuss the other characteristics which distinguish transportations, and which are of very unequal importance.
-To classify along the presence of one or two computers is almost equivalent to the
distinction between half and full bootstrap, since these two methods are defined after this
characteristic.
-It is therefore much more significant to consider the physical distance between the computers, if there are two. Thus, P-Iris-80, P-Sigma and P-2900 did not encounter any
problem in this respect, since both machines were in the same building. On the contrary,
there are 600 km between Toulouse and Nice (P-Iris-50) and 1500 km between Zurich
and Belfast (P-1900). This problem has been solved with a simulator of the 1900 on the
6000 in the case of P-1900, and by a method which guarantees the correctness of the
product (all initial work is done on the source computer) in the case of the first part of
P-Iris-50.
-The remaining characteristic concerns the implementation languages used for writing
the compiler or transporting it. As we shall see, they become essential when the fact that
one or two computers might be used is taken into consideration. Of course, Pascal is the
preferred writing language if one wants to obtain a self-compiling compiler. I t is used
in the following situations: when a Pascal compiler running on computer X is transported
on a computer Y (from P-6000-1 or P-6000-2 to I C L 1900, C I I Iris SO, IBM 360 in
Grenoble,14 from the latter to C I I Iris 80;l4) when a Pascal compilerf or an abstract
computer is modified for an actual computer (P-PDP-10); when filling the holes in
a trunk compiler (P-Hitac-8000, P-2900, P-Iris-50) ; when implementing P-6000-2
using P-6000-1 or P-1900-2 using P-1900-1. Pascal-P and Pascal-E are special cases
(see Figures 7 and 10): the actual compiler, which generates intermediate code, is
written in Pascal, but the translator which follows may be written in Pascal or anything
else.
Not many Pascal compilers are written in another language than Pascal. P-6000-1
used a translation by hand into a pseudo-assembly language for initializing the bootstrap

Evaluation of the examples
The considered indications
Many different measurable indications may be considered when trying to give an
evaluation of the different examples listed in the subsection Inventory of the cases considered.
The relative weight which is given to each of these indications cannot be established in a
unique fashion, since different people have different motivations, aims and priorities when
they decide to implement a new programming language on their computer. Therefore, it is
not our intention to attempt an absolute and objective classification of the qualities and
success of the different examples. We prefer to provide a table (Figure 15) which displays the
results of a coarse evaluation, according to sixteen indications which will be explained below.
These indications may be further classified into three categories : those which characterize
the transportation or implementation work, those which describe the product of this work,
and finally the by-products.
The amount of work for a given project is generally evaluated in man/year (or man/
month) units and nothing else. Although such a figure is interesting, it is really not sufficient,
and can often be mi~leading.~
The final result obtained in this type of evaluation can vary
to a great degree, depending on which of the different segments of the total task were taken
into account. In some cases, even a 50 per cent difference cannot be considered significant.
If we want such an evaluation to be more realistic, we think that the following three factors
should always be considered: the size of the team, the initial competence of its members
and the real time for realizing the task. The first and the last allow us to take into consideration the fact that two persons working half-time is not equivalent to one person
working full-time, and that the work done by a person in 6 months may not be equated with
the work done by two persons in 3 months. The initial competence of the team members
is also very important, since the time necessary for learning the source language, the object
language, or even compiling itself, may or may not be considered part of the implementation
task.

T h e qualities of the product are not always very easy to compare, since many, for
example, measure compiling speed in number of cards crunched per minute, but omit to say
something about the performances of the machine (and the operating system) upon which
this measure is taken. We prefer, when possible, to give a vague estimate of the performances
in size and speed of both the compiler and the object programs, by scoring on a scale of 0
(very bad) to 5 (very good), and by comparison with an average Fortran implementation on
the same computer. These four indications are the most objective ones, but four others are
equally important : the ease and naturalness with which the compiling system is incorporated
in the host operating system (a compiler which produces binary code in link'age editor
format is better than another one which uses its own absolute loader); completeness of the
language implemented (some features required by the standard report1' may have been
omitted) ; conformity to the standard report (some features may be differently understood
and implemented, some additions may yield incompatibilities) ; reliability of the compiler
and the object programs it produces.
Finally, we include four measurable indications which describe the by-products of the
implementation of the compiler. T h e amount of rewriting of the compiler is partly a
measure of its portability, and partly a way of knowing if the new compiler is really a new
product or only a copy of the old one. T h e other three indications evaluate the interest of
the transportation: if it uses several implementation tools especially developed for it, are
these tools usable for other things (interest of the by-products) ? What is the interest of the
work itself ? (Since Pascal implementations are almost always done in Universities, it is
important to know whether such a job may be the subject of a thesis or a term project, or
is only a development work.) What is the feedback on the source and tools of the transportation ? (Many transportations could reveal defects in the initial compiler, as well as in the
assembler, linkage editor or other implementation tools.ll)

The table was filled in by the following method. First, by consulting all the available

the usage of Pascal-P, for which we used our own experience on the CII Iris 50; the methods
of half-bootstrap and writing from scratch.
We tried to signal carefully some differences of interpretation which must be given

RECOMMENDATIONS AND CONCLUSIONS

Choice criteria for a potential implementor
An interesting result of the classification and comparison of implementation methods
made in the preceding sections should be that, for somebody willing to implement a selfcompiling compiler, and especially a Pascal compiler, choosing from all available methods is
made easier. We will discuss several selection criteria, and apply them to our examples.
These criteria may be classified into three categories, concerned with the computer upon
which the compiler should be implemented, the team which will do the job and the
characteristics which must be satisfied by the intended product.
The computer
The first criterion directs the choice between a half and a full bootstrap. If you have
access to a computer on which Pascal is already implemented, and if this site is not far from
your own, then a half-bootstrap is possible (but not necessarily desirable, for other reasons).
The distance between the two computers may make necessary the construction of some additional implementation tools (as for P-1900- 1 and P-Iris-50), especially if travelling time
must be minimized. If no other computer is available, you must use a full bootstrap.
The differences between the object computer, for which the model compiler was designed,
and your computer are important, since they determine, at least in part, the amount of
rewriting which will be needed. The figure may vary from 40 per cent to almost nil,
depending upon the particular situation.
The various programming languages available on your computer is another important
factor since one is needed for writing the compiler, and another one might be used in
transporting the compiler. If a rudimentary Pascal compiler already exists on your computer,
such as the ones produced with Pascal-P, Pascal-J or other similar methods, and if it is
economically usable, then undoubtedly the best solution is to use it as a tool for writing the
intended compiler, probably by filling the holes in a trunk compiler. If you have a good
implementation language, such as Algol W, BCPL, Bliss or XPL (but not Fortran or

PL/I), using it for writing a compiler from scratch is a solution worthy of consideration,
but it is very important to be aware of the significant pitfalls involved; a complete compiler
must be written anew, it will not be self-compilable, and there are great risks of deviating
away from the standard language definitions. The amount of work is largely reduced if a
compiler-writing system is used (as in Reference 38), but the risks of deviation are probably
higher, because of the idiosyncrasies of this system.
Another language may be used during the transport, but not for writing the compiler.
One example is the use of a macroprocessor or macro-assembler. If you have a good
implementation of Stage2, for example, using the Pascal- J method may be considered as a
way of obtaining a first compiler on your machine, but the drawbacks are that this compiler
will be a two-pass one, with a very slow second pass. If you have no suitable macroprocessor,
implementing Stage2 is
but improving it, up to a non-interpreted version, is not a
trivial job, and it is probably too much preliminary work to first have to implement Stage2,
then Janus, then Pascal-J, and only then, be able to work on the intended Pascal compiler.
Another case of a language used only during the transport is the one used for implementing
the P-code interpreter. This program can be easily written in Fortran or assembly language,
and it is probably the fastest method available for obtaining a somewhat restricted and
really inefficient compiler. However, this compiler may be used for some experiments or
student jobs, but not for production work, and it cannot be used for implementing a real
compiler, except on big computers and with very enduring computer centres : to monopolize
the computer €or 5 hours or more, each time you want to compile your new compiler, is
simply unthinkable in normal situations, and every attempt to use Pascal-P as an implementation tool on medium or small computers has been a failure (to our knowledge).

The implementation team
Either the team already exists, or there are financial and human resources for creating it.
An obvious characteristic of a team is its size, which in almost all cases we know of was
small. A team of three persons appears to be a maximum, while a person working alone
seems to yield very good implementations but takes a somewhat longer time. Generally
though, a team of two persons is seemingly best suited for the task, and it is the particular
implementation method chosen that dictates what will be the total implementation time
needed. Of course, if 1 year is required by one person, one cannot conclude that half a year
will suffice for two persons, or even three.4 If only one person is available, either be prepared
for a comparatively long delay, or choose a fast (but inefficient) method like Pascal-J or
Pascal-P.
The initial competence of team members is a most important factor, which in fact explains
the marked differences in the quoted figures (Figure 15) for the ‘amount of work’ needed.
While a graduate student can easily implement an interpreter for Pascal-P or the macros
for Pascal-J, a thorough knowledge of Pascal, of the object computer and of compiling
techniques are prerequisites for the task of filling holes in a trunk compiler. Furthermore, the
construction of a completely new compiler should not be assigned to somebody with no
previous experience in writing a simpler compiler, from scratch or by using a compilerwriting system. Complete compilers, constructed from scratch by students learning
compilation as they go along, cannot usually be used as production tools, and upgrading them
to this level is generally not worth the trouble.
Independent of the qualifications of the team members is the notion of a ‘participatingtime’ contribution. For example, if the team members can only work part-time on the
project, this will of course increase the total time required, and it will also be advantageous

to use implementation methods better suited to this type of situation (Janus, Pascal-P).
On the other hand, a method involving the rewriting or redesigning of some parts of an
existing model compiler requires sustained and continuous participation.
Finally, there is another influential factor which emerges if the team operates in a university context. Since university managements generally provide funds and manpower for
what they call research and not for development, the proposed implementation project must
involve some research work. Thinking along that line, one concludes that only the
rewriting of an important part of a model compiler, or the invention of a completely new
implementation method, may be considered. On the other hand, if the work is to be
accomplished as a term project for undergraduate students, one should only use the simplest
and fastest methods of implementation, because of the time factor involved.

The intended product
Of primary importance for any expected product is the delay involved in obtaining it.
It is very frequent that people choose one solution preferably to another, whatever the
long-term consequences may be, only because of a shorter delay. Fortunately, in our case,
the fastest solutions, which yield implementations with the poorest performances, may
often be used later as tools for implementing better compilers. The consequences of a choice
made only on the basis of a short availability delay are therefore not very severe, except in
the case of Pascal-P, if the interpreted compiler is unusable as an implementation tool.
Performances and availability delay are contradictory requirements, as we have implicitly
demonstrated. All the methods which allow implementation of Pascal in 4 man/months or
even less yield a two-pass or interpreted compiler, requiring a large memory and producing
inefficient programs at a slow pace. Only after further refinements can they yield a better
version, and the only really good implementations are those in which a ‘real’ compiler was
tailored to the object machine. The dilemma is therefore clear: you can quickly implement
an experimental tool, but you need time and manpower to implement a production
compiler. Of course, the time and manpower resources needed are much less in the case of
self-compiling Pascal compilers as compared to ‘classical’ implementations.
Another requirement expected of the intended product is its conformity to the standard
language definition of Pascal. No implementation method needs to deviate from the
standard, but some of them do not discourage deviations, vix. those in which the compiler
is written from scratch, using a compiler-writing system or simply a compiler-writing
language. On the contrary, use of a trunk compiler strongly encourages conformity, since
the implementor must consciously modify existing code to deviate in any important way.
Some implementation methods yield only a subset of Pascal, especially Pascal-P, but it is
a less severe problem, which nevertheless must be considered beforehand.
Some implementation methods may produce a compiler with desirable particular
characteristics. For example, the fact that programs generated by a Pascal-P compiler are
interpreted may be useful for student programs. The two passes of Pascal-J and Pascal-E
may allow more flexibility for separate compilation of procedures or optimization of object
code. Generating code directly for a linkage editor is probably easier with a monolithic
compiler such as the trunk compiler. These characteristics are less important than the
preceding ones, but should play a role in the final choice.

Conclusion
The most important conclusion which can be made after this study is that it is quick and
very easy to implement Pascal on any large- or medium-size computer, provided you do not

when you have a workable implementation, to refine it until you have a really good production tool, by using the main idea of a self-compiling compiler. There is both a positive and

of the language on almost any computer (57 computer series had a Pascal compiler at the

such as P L / I or Algol 68, or machine-dependent languages such as Bliss or BCPL.
T h e negative consequence is the proliferation of implementations which bring to life
‘language-deviates’ (of the 86 different implementations recorded, 16 at least were done

Programming languages which are not supported by a powerful vendor or an international
organization are submitted to the following dilemma: if the author tries to keep a very
tight control on the language, does not provide compilers in readable form and even requires
