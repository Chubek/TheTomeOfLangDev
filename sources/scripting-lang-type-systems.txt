Abstract
Type systems play an important role in the design of programming languages, they prevent programs from having non-correct behavior. Typically,
type systems are expressed in two ways, type-checking and type inference. The
type information presented on local variables and method arguments makes the
difference in choosing one technique rather than the other. Type checking is
a derivation type inference. In literature, the time when type-checking occurs,
compile or run time, classifies them in static and dynamic.
We will take a look on the type systems of some scripting languages. In this
paper, we will focus on JavaScript, Python and Ruby. Most scripting languages
use dynamic typing. However, we will see some recent work on providing them
with static type-checking, soft-typing and type inference. We will discuss about
their dynamic and lightweight properties and also about the trade off between
the advantages of using static type-checking and the preservation of their properties. We will talk about the object-oriented features presented in scripting
languages looking at Smalltalk [Ing78] as the first object-oriented programming
language. We will look also at recent works on pluggable type systems [Bra04,
ANM06] and on PyPy[RP06], a translation tool from Python to C.

Introduction
Type systems define how programming language expressions are classified due
to the type of value they calculate. The typing rules presented in them prevent
the program from having various programming errors, from division by zero to
message not-understood errors. The type information presented in the syntax
of a programming language classifies them in type inference and type-checking.
Type checking is the process of type constraints verification. The process
can occur at compile time leading to static type checking or at run time leading
to dynamic type checking.
Static type checkers do not use run-time expression equivalence. They type
variables only once. Some benefits of static type systems are as follow
• early detection of some programming errors
• abstraction, types are used to construct module interfaces and a clear
interface leads to a more abstract style of programming
• documentation, the type information in an interface provides a documentation for the program
• optimization, given the type of a variable, e.g. the system generates the
precise amount of memory for it
However, there are some disadvantages of static type-checking. Mandatory typechecking may constrain the expressiveness of the language. That is, if the static
type-checking is mandatory and so some legal programs that are ill-typed will
be rejected by the compiler; i.e. if (true) then 3 else htype error i.
The reliability of software is completely delegated to a static type system.
Real systems are hard to formalize leading systems to have simplified assumptions. The assumptions do not reflect the reality and any reasoning made on the
formal model. Implementations will have bugs even though the type systems
will well-type them. By this we conclude that type systems are not a reliable

3

source of truth. Static type systems add type annotations on variables and on
functions making programs more complex.
Variables in languages with dynamic type systems can have over time different types. The type of a variable depends on the type of the value the variable
is referring to at that moment of execution. These kinds of systems do not need
type annotations, making program less complex than those with static type systems. However, they do not have the benefits of static type systems.
Type inference is the process of deducing type information from the program. The type of an expression can be deduced by the type of variables and
constants contained in it. The type of variables can be deduced also by using
the Robinson’s [Rob56] unification algorithm; i.e. in the expression X + 2, the
type of X initially will have type A, then the typing rule for + operator will
force A to be Int. If X is used in other parts of code refereing a string then it
would be signaled as an error by the system as the type information deduced for
a variable is propagated all over the program. The advantages of type inference
are program less complex because of the lack of type annotations. Type inference is performed at compile time so it provides early error detection as static
type checking. Type-checking is a derivation of type inference where the type
information is present in the syntax of the language.
Type systems can be divided also in two category regarding the importance
of being strict to the typing rules, weak and strong type systems. Weak type
systems support either implicit type conversion, overloading or both. Whilst,
strong type systems do not allow type conversion.
The Smalltalk [Ing78] programming language is the first programming language that introduced the principle of communicating objects. The principle
is used in the construction of execution model of object-oriented programming
languages. Smalltalk provides many programming features as modularity, emphclassification, polymorphism and factoring. It is interesting to note how these
features are implemented in Smalltalk as they are also used in the scripting
languages considered in this work.

allows value conversion which for some situations would be important but in

Smalltalk
The Smalltalk [Ing78] programming language is the first programming language
that introduced the principle of communicating objects. The principle is used in
the construction of execution model of object-oriented programming languages.
The goal of Smalltalk designers was the creation of a simple programming language for single users and a stable kernel for it.
It is important to have a metaphor in mind before constructing a new programming language. The metaphor should be applied to different areas and
expressive to model complex systems. The metaphor used by the designers
of Smalltalk was the one of how humans think and communicate. By Ingalls,
creative thought can be viewed as the spontaneous appearance of information
in the mind. Language makes humans to abstract and store information in
the mind. Communication in humans is achieved through shared context, and
human language is built around such environment. This is an analogy with
computers as well.
The world is a vast universe of objects. To take part in the world one must
draw distinctions on the environment that surrounds it. Each object in our
universe has a life of its own. In the same way, the brain provides for each
processing along with storage of each mental object. Computing can be viewed
as an intrinsic capability of objects that can be uniformly defined by sending
messages.
Objects were introduced to model structured information and messages were
introduced to model processing. The execution model of Smalltalk delegates to
objects the control of the program and not to functions names as the functional
paradigm does. That is, the model sends messages to objects to have results of
computing.
Smalltalk has a different syntax from other programming languages. It uses
⇑ to return values and whitespace for method invocation. The message code is
inserted between rectangular brackets, [ ].

2.1

Programming Language Idioms

The Smalltalk model provides modularity, classification, polymorphism and factoring as part of its organization.
• Modularity. No interdependencies in complex systems because they make
the system even more complex.
• Classification. Smalltalk classifies similar objects using the notion of class.
• Polymorphism. A program should declare that its protocol works for a
superclass and not only for any particular subclass. Languages that do
not support polymorphism will make extension of programs difficult and
will increase the possibility of programmers making errors.
• Factoring. Each component of the system should be in only one place.
The benefit of this feature is that we do not have to recompile whole part
of systems when a new trait or object is added. This feature is achieved
by Smalltalk using messages.
Smalltalk uses uniform reference to objects. That is, it associates a unique
number to an object in the store, message sending and classes to model modularity. The answer to a message is implemented by a method. The notion of
messages is helpful not only for factoring but also for information hiding, in the
sense that the user will not access the method code. The notion of class is similar
to other object-oriented programming languages; it is basically a static store of
fields, message names and methods that implement messages. Another benefit
of messages is the type independence code. Polymorphism allows much share
of code. As we well know the first mechanism that profit from polymorphism is
subtyping by subclasses.
The notion of built-in functions is implemented in Smalltalk by a set of
useful superclasses from which other classes are derived. The most general one
is Object with the classic set of messages: printing, examining and altering
the content of an object. Smalltalk also support useful classes for graphical
applications. The class Window is the interface of the language for programmers
to the devices such keyboard and display screen.
A class in Smalltalk is defined by its name, names of fields, messages that
access the fields and a list of messages with their implementation as well.

2.2

Internal Design

Storage Management. Smalltalk uses reference counter to achieve automatic store management. The virtual machine assigns a counter to each object
in the memory. The counter keeps the number of variables referring an object.
The designers of Smalltalk used this technique rather than mark-and-sweep
garbage collection by the fact that the computational overhead introduced by

8

freeing the memory is spread uniformly at runtime.
Compact Object Code. In virtual memory systems, we have to consider
the overhead introduced by the change of working set. We need to have a compact code to reduce the number of working set swaps. Smalltalk translates its
source code in compact syllables. The translated code is just parsed source code
tokenized. It has postfix notation for later use by the stack of the interpreter.
In the static structure of Smalltalk, the classes refer to the translated code for
each method and also to source code of the method. The dynamic structure of
Smalltalk is similar to the one of other programming languages. Each program
at runtime has its program counter, evaluation stack and reference pointer to
store the computed value.
Smalltalk uses smart microcoding to implement common operations as +,
- etc. to omit the overhead introduced by loading a new method invocation
context.

3.1

Dynamic Semantics

A small step operational semantics for the core JavaScript is presented in
[Thi05]. The reduction relation shows the change of the store and expression,
Σ, l0 , expr → Σ0 , epxr0 . The left hand side of the reduction rule contains the
store of objects, the address of the current activation object and the expression
(statement) to be evaluated. The right hand side contains the modified store
and the evaluated expression (statement).
The store is a function from locations to objects. Objects in the store are
represented as a mapping of properties name to values. Values are formed by
locations, booleans, numbers, strings and function closures. The language distinguishes three special property names: VALUE, up and this. Functions in
11

JavaScript are treated as objects so they need to be stored in a particular location of the store. The property name used to store functions is VALUE. VALUE
is used also to store wrapper objects of primitive data types. The up property
stores the location of the next activation object. It is used in the execution
of a method body to track a non bound variable in the scope of the method.
The up property allows using variables that are not defined inside the function
body or as parameters of functions. It is used at the evaluation of closures. The
this property keeps the receiver object of a method and it is used in method
calls and constructor functions. For its relevance, it is considered as a special
property.
The logic of the reduction rules is standard as in other object-oriented programming languages, under the light of what discussed above.

3.2

Soft Typing for JavaScript

Thiemann [Thi05] presents a soft typing systems for JavaScript. The type system does not control the changes on the interface of objects. Message-notunderstood errors are not considered by it. The main goals of the type system
are the identification of value conversions and flagging silent wrapper conversion. The type system uses singleton types to type base-type values. This will
increase the precision of accessing and updating the properties of objects.
var a = ”bug test”;
a.x = 51;
alert(a.x)
It will not print 51 because the variable a refers to the base-type string and
not to the wrapped object that contains the property x.
A type of an object is formed by two parts. The first part of the type
presents the nature of the object which could be a wrapper object, function, or
list of properties. The second part of the object type is a row type where all
the types of properties the object own are recorded. The row type uses string
constants as labels for properties. When typing a function, the identifiers have
to be converted in string values, (arguments variable). Also at the end of the
row type there is a default type for all not defined methods. JavaScript allows
to call functions with more or less arguments than there are in the function
definition. Functions are always wrapped into objects.

4.1

Type Inference

Dynamically typed languages are slow because dispatching and binding are
solved dynamically. The type system controls the type of the operands ev15

ery time during operations. The virtual machine should find which part of code
to execute and also it should control if the operands have the correct type for
the operation. Dynamic typing restricts some of the optimization the compiler
can have.
Starkiller [Sal04] is a static type inference algorithm for Python. Its goal
is to remove safely some of the type checks and most instances of dynamic
dispatch and bindings from the dynamic type system. However, Starkiller is
not a complete type inference for Python, some of its dynamic features are not
solved by the algorithm. These features are dynamic load of modules, eval
and exec. The eval function evaluates a single expression. It cannot execute
statements, but can execute functions which execute statements. The exec
expression executes statements; i.e. eval(’1+1’), exec(’y=1’). Programs
that contain these constructs are rejected by the algorithm.
Starkiller constructs a data flow network to simulate the dynamic behavior of
a program. The structure is a directed tree where the nodes represent variables,
expressions, functions, method calls, classes and objects with the set of possible
types they can have at runtime. Nodes are linked to model the data-flow of
the program. On links there are constraints establishing a relation on the type
subset between nodes. That is, the receiver node’s type set has at least all the
type set of the sender node. At the beginning the type set of nodes is empty
except of constant nodes. When a new type is inferred by a node, it is added
to the type set of that node and propagated to other receiver nodes.
For an assignment expression, x=expr, the tree is composed by two nodes
one for x and another for expr. A link from expr to x is established so that the
type set of expr is copied to the type set of x.
When Starkiller encounter a function definition, it generates two nodes, one
for the function name and another one with the function definition. Then, it
links the function definition node with function name node. Nodes generated
for the arguments of the method are linked to the definition node.
During a function call Starkiller creates a function call node. It links the
function name node to the function call node. It links also the actual argument
node to the call node. At the end, Starkiller adds a link from the call node to
the node where the returned value lie.
Parameterized polymorphism of functions mandates the type inference algorithm to have the Cartesian Product [Age05] of the sets of arguments type, self
included. The cartesian product will increase precision of the algorithm rather
than merging the types of the arguments. The product is calculated in method
calls nodes. Each element of the list is a k+1-tuple, where k is the number of
arguments. For each tuple a template is generated if it is not already defined.
A template for a method is the graph of expressions inside the body of the function and the arguments with the appropriate links between them. Templates are
shared to other function calls. For each template defined the returned type is
computed. At the end, the union of types returned by each template is returned
to the call node.
Class and objects are typed in the same way as functions, a name node and
a definition node. The cartesian product of base class and non local references
16

set types is taken to form the class type. The interesting point is when a new
method is added the type of the object(class) can not be changed because it is
immutable. The type object has a reference to the definition node that produced
it and informs it about the new attribute. Then the definition node will generate
new object(class) types and propagate them through the tree.
Starkiller is flow-insensitive. It does not pay attention when a certain value
is assigned to a variable; i.e. num=4, num=3.2, in the data flow tree the node of
variable num will have a type set int, float. Starkiller will be less precise than
a flow-sensitive algorithm. Trivial cases of insensitivity can be solved using a
static analysis on reachable definitions, at each program point which are the
readable variables.

PyPy

The PyPy [RP06] project consists of constructing a virtual machine for Python
in Python. It is difficult to have efficient, portable and flexible virtual machines.
The virtual machine is going to be specific of a certain platform, C/Posix, Java,
CLI/.NET, etc. Some architectural decisions in the design of a programming
language affect the efficiency of its virtual machine. The garbage collector code
is spread all over the virtual machine code making the code more difficult to
write and not very clean. The issues become more complex when we try to
implement dynamic languages considering their dynamic features. If we write
a virtual machine for a dynamic language in a dynamic language and then
translate it into a low-level language, we achieve a flexible and expressive virtual
machine.
The aim of this work is to present a translator tool that translates the virtual machine of RPython, a restricted part of Python, written in RPython into
a low-level language, i.e. C/Posix, in an efficient way. The translator tool will
compile subsets of Python constructs to low-level languages. The translation
process is divided into several steps:

Ruby
Ruby was created with the idea of having an easy to read and easy to write
code programming language. The main goal of the Ruby system is to help
programmers to write code in a natural way for them. Designers of Ruby tried
to construct a language that preserve the Principle of Least Surprise. That
is, a program written in Ruby will behave as the programmer projected it.
The creators of Ruby wanted to blend best features of popular programming
languages as Smalltalk, Java, Python and Perl in an efficient way.
Ruby is an object-oriented programming language with a rich class library
and implementations of several design patterns: Command, Iterator, Factory,
etc. Every thing is an object. Integers might seem as objects in the programmer
eyes but the virtual machine has a side implementation, not as object, of them.

Optional, Multiple and
Pluggable Type Systems
Mandatory type systems are all those type systems where the legality of programs depend by them. That is, programs must successfully pass the typechecking process. The main group of systems that represent this category is the
static type systems. Advantages and disadvantages of mandatory type systems
are those of static type systems presented at the Introduction chapter. It would
be nice to have systems that maintain the advantages of static type systems but
to not maintain their disadvantages. Optional type systems try to keep the advantages of static type systems and not maintain their disadvantages. Optional
type systems lead to another kind of type systems, pluggable type systems.

6.1

Optional Type Systems

Optional type systems[Bra04] are characterized by two properties, the first is
that dynamic semantics is independent of the type systems and the second
is that type notations are not required in the syntax of the language. It is
important to note that, by the definition, optional type systems can provide
static type systems to dynamically typed ones without changing the syntax and
the dynamic semantics of them.
Constructs such as public fields, class encapsulation and overloading do not
preserve the first property. These constructs form a dependency of the semantics
on the type system. Class-based encapsulation introduces a dependency of the
semantics to the type systems. Static checking can not prevent the access to a
private variable of an object inside the class that has defined it. The dynamic
semantics has to check that there is no such access. Overloading can not be
solved by the dynamic semantics without the typing information present on the
arguments of methods for distinguishing one method than the other.
Programming languages that will use optional type systems will not have the
constructs discussed above. However, this modification should be considered as
23

a benefit and not as a limitation. All these three constructs are well-known in
software engineering; they are sources of aliasing and security problems. The
modularity introduced by the lack of dependency of the semantics rule to a type
system can increase the number of programs expressed in the language. Type
systems con evolve more quickly than programming languages. Programs that
were untypeable before by the type system can be typeable by a modified type
system without requiring change of the semantics rule.
The idea of optional type systems can be applied to type inference. Type
systems should be independent on type inferencing. Dependent type systems
will restrict their expressiveness; i.e. the Hindley-Milner type system used in
ML cannot support polymorphism by the fact of using type inference as part of
the type system. The concept of type inference as soft typing is abused sometimes leading to restrictive type systems. Building the type inference algorithm
separately from the type system, i.e. as part of IDE, will lead to multiple type
inferencers.

6.2

Pluggable Type Systems

The independence of the dynamic semantics from a type system induces the
idea of having type systems as plug-ins[Bra04] onto the language. We can have
zero, one or many type systems plugged in the languages. A programmer that
is developing a software where aliasing is a big issue can cast a static analyzer,
that deals with aliasing, as type systems. A first problem that comes up using
multiple type systems is how to integrate them in a language. One solution
could be to use metadata. Metadata allow programmers to add user-defined
annotation onto the Abstract Syntax Tree. Types will be a kind of metadata in
these kind of language.

6.3

JavaCOP

Traditional type systems can not provide all kinds of constraints a programmer
may want for the simple reason that programming language designers cannot
foresee all them; i.e. to not assign a null value to a non primitive variable, to
not let escape a certain object from the package, etc.
JavaCOP is a framework to express user-defined type systems. It is an implementation of pluggable type systems for Java.It provides a framework to define
new constrains for Java programs. Basically, JavaCOP is a language to write
typing rules for new type systems introduced by a programmer. User defined
annotations are considered as metadata by the javac parser and are inserted in
the AST, later the AST is enriched with existing type systems information and
type checked by the rules of the new type system. A big line schema of this

24

process is as follows:

Java program → PARSER → AST → JAVA TYPE CHECKER → Augmented AST
→ PLUGGABLE TYPE CHECKER → T ypechecked AST →< other processes of javac > .
User-constraint systems have been introduced before but the following reasons makes them different from JavaCOP.
• Type annotations are considered as metadata. The user defined types
annotations have to be added next to type annotations to be considered
as metadata, so they have to be put during declarations, specially in class,
variables and field declarations. JavaCOP makes the metadata facility of
Java more powerful because it allows users to introduce additional type
specifications.
• JavaCOP is a declarative language to give a semantic to the user-defined
type annotations. The programmer just specify a constrain to achieve in
JavaCOP and the underlying model takes care to implement it. The rules
of the constrains can be written in Java but they have to use the AST’s
API. This will be another level of difficulty by programmers to implement
rules.
• JavaCOP employs the Java type system information to use for implementing new rules. The enriched AST is equipped with the information of the
Java type system.
• JavaCOP preserves the modularity of the Java type system. That is,
Java typechecks classes or interfaces in isolation using only interface information for other referenced types. This information is gathered by the
bytecode of the other classes, so there is no access to the source code.

The JavaCOP framework extends javac by changing its structure. There is
a translator tool that translates JavaCOP rules in Java code and checker that
checks the translated rules.

6.3.1

Details of JavaCOP

The AST of javac produced by the parser is an abstract tree of nodes, where
nodes are Java program constructs. The JavaCOP checker receives a typed AST
by the Java type system. Javac does not access nodes of the definition of classes,
methods and fields of other compilation units. It extract the information for
super type, interface type, metadata needed by the bytecode and stores it in
Symbol objects.

25

Each rule declaration is applied to a particular AST node. Pattern matching
on rule arguments is used to find out where to apply a rule. Arguments of the
rule has the same type or subtype of the AST node where the rule will be applied. JavaCOP supports user-defined subtyping relationship. The programmer
can express the relation of subtyping explicitly in the syntax of the rule. The
framework will take care to check if the subtyping constraint holds in the nodes
where this relation might be used, assignment statement, parameter passing,
result returning and casting.
JavaCOP constrains are built-in methods on nodes and symbols. They are
pure predicates. These rules are enforced by the JavaCOP API. It supports
some Java primitives types, String and Lists, operations on them included, to
enrich its expressive power.
JavaCOP has two constructs to provide quantification: forall and exists. The
first one is a universal quantifier and the second one is an existential quantifier.
The syntax of the first one is similar to the Java for. These quantifiers are
defined on List objects.

Strong and dynamic Type System

There are a lot of dynamic features into the languages considered above but
observing the softwares developed with these languages, these features are not
used a lot in them [Thie05, Sal04]. It is a waste of performance not utilizing the
optimizations of static type systems but using static type systems for dynamic
languages will reduce the legal programs expressed by them. In the other hand,
the parts of code that use dynamic features are very imported to the existence
of a software.
Type inference might be a medium solution. Even thought it does not provide type inference for all constructs, eval, exec, dynamic module loading, it
provides good a inference algorithm for adding, changing and removing dynamically methods from objects or classes.
Soft typing can be considered as a relief to dynamic typing. The philosophy is to have a static type system without changing the expressiveness of the
language. To check statically without changing the expressiveness what can be
done statically and to delegate at runtime what can not be done statically.
In conclusion, one way to provide static checking for dynamic featured languages would be to have a mixture of the two systems discussed above. It might
be interesting to have a double layer type checking system where the first one is
the type inference algorithm that prevents from having message-not-understood
errors at runtime and a second layer is the type system.
