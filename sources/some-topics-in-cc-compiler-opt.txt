ABSTRACT. Many compilers for higher order languages attempt to translate the source code into
"good" object code. Cocke and Schwartz have described an algorithm for discovering when the
computation of an expression is redundant (common), and when it can be moved to a less frequently
executed region of the program. The present paper includes a tutorial presentation of their basic
methods, along with a number of improvements and extensions. These include simplification of the
solution method, to save a pass; extension of it to treat the safety constraint, handle multi-entry
regions directly, detect additional commonality and code motion after unsafe code motion, and
decide where moved code should be put; and combination of the algorithms for commonality and the
dead condition, making use of important work of Ken Kennedy.
The methods here applied to collecting information for use in code optimization include general
algorithms for solving a set of linear equations in Boolean algebra. The algorithms are most useful
when the coefficient matrix is sparse.

Introduction

As long as there have been machine independent programming languages, there have
been compilers which attempted to produce "good" code for the programs written in
such languages. Much of the first FORTRAN I compiler was devoted to the optimization
of the object code, on the farsighted realization t h a t acceptance of FORTRAN would
depend greatly on the quality of code produced by the compiler. The very idea of compiling, rather than interpreting, the source code implies some concern with efficiency.
This paper presents and explains a class of algorithms for performing the code optimizations known as common subexpression elimination and code motion (hereafter
called CSX-M). The basic method was invented by John Cocke (IBM), who based his
work partly on some unpublished ideas of Vyssotsky. The idea of presenting the algorithms as the solution to a set of Boolean equations is due to Jack Schwartz (NYU), and
a description of the kernel ideas is available in [2]. The present paper attempts to clarify
the connection between the solution of the equations and the program being optimized,
and presents a number of improvements and extensions to the basic method, made principally by the author; some of the ideas are also due to Karl Balke (now at Burroughs),
along with Kerry White and James Anderson (both CSC). The new material includes a
simplification of the method somewhat, to save a pass; extension of the method to treat
the safety constraint and compute the profitability values; demonstration of the connec=
tion between profitability and dead analysis; combination of the solution for CSX-M,

Elimination of common subexpressions and the movement of code to lower frequency
areas are closely related. Suppose that a point P in a program is a compute point for some
expression--say a + b; that is, in the original program, the computation of the expression a + b occurs at point P. If during execution, the current value of a + b is available
at P - - t h a t is, the current value has always been computed when P is reached--then the
occurrence of a + b at P is redundant, or common, and can be eliminated (the previously
computed value is used). Likewise, if the current value of a + b is available on some
paths to P, but not on others, and it is possible to place compute points for a + b along
all paths where its value is not available, then the compute point at P can be eliminated
(since a + b is now available on all paths). This process is code motion; Figure 1 shows
two examples.
I n the second case, the value of a + b is available along the latching p a t h - - i n a sense,
it is common with itself. Finally, if the value of a + b is unavailable along all paths to
P, it is impossible to reduce the frequency of computation of a -t- b by code motion, since
(Kirchhoff's Law) the execution frequency of P is the sum of the frequencies of all entry
paths to P.

2. Information Needed for Optimization
An optimizing transformation must produce code that is equivalent, in some well-defined
sense, to the original code. The definition of equivalence commonly used is that the
altered program must produce the same results as the original--output variables must
have the same values, printed output must be the same, etc. Note that the altered program cannot sensibly be exactly equivalent to the original--it should occupy less space,
or require less execution time, for example.
For the optimizer to transform a program correctly, it must be supplied with information about the data flow and the control flow of the program, and about source language
constraints on changes. For example, variables must be referred to by name (or symbol
table entry), and equivalences or overlays must be known. The set of possible destinations must be known for each GOTO statement or subroutine call. In the absence of
complete information, it is always possible to make a "safe" assumption--for example,
to assume that a variable referenced through a pointer is equivalent to all variables in
the program, or to assume that a branch has at some time every labeled point in the
program as its destination. Clearly, the more precise the information, the better the
optimized code, in general. Collecting information of this sort may not be easy, but often

3.

Bit-Vector Optimization Method

3.1. BASIC ASSUMPTIONS;DEFINITIONS. The method is based on a view of a program
as a collection of expression compute points and definition points, together with a specified
control sequence (i.e. flow graph) connecting the different points. The identity, or name,
of an expression is an ordered n-tuple consisting of the operation to be performed, together with the names of the operands (themselves either simple variables or other expressions). That is, the name of the expression a 4 b, wherever it occurs, is something
like ( 4 , a, b); the name of a 4 b.c is something like ( 4 , a, (., b, c)). A definition point
for an expression arises from a statement which assigns a new value to any of the operands
of the expression. Thus a definition point for the expression a 4 b.c would occur, for
instance, at the statement a : = x 4 y, or b : = b 4 1, or at a subroutine call of a subroutine which assigns a new value to a, b, or c (or to any equivalent variables). For
purposes of these algorithms, a subroutine or function call is considered to be an operation
which has a known set of operands, and which assigns new values to zero or more variables (which may be arguments, in COMMON, or otherwise accessible to the subroutine).
Operations such as subscripting or selection via a pointer are treated just like other
expressions. (For some machines it might be desirable to treat such an operation as producing two results: both the value and the address of the selected variable. One way to do
this is b y explicitly including in the code string both the selection operator and the dereferencing operator--as it is called in ALGOL 68.) Whenever the value of an expression
is explicitly redefined (e.g. the expression appears on the left side of an assignment
statement), this typically constitutes a definition point for a class of variables--all with
the same array name, for example, or all accessible via the same pointer. That is, the
statement z[i] := x 4 y is a definition point not only for z[i], but also for z[j], z[i 4 1],
or z with any subscript at all (ascertaining that particular references to z[i] and z[i 4 1]
always designate different variables can sometimes be done; this is not covered herein).

including references to variables with computed names.
The algorithms make no changes in the identities of expressions. Any folding in or
combination of constants is assumed to have already taken place, if it is to occur at all.
No reparsing to discover additional common subexpressions is done. A. sensible comproraise is to list all expression operands in some canonical order, based on their locations
in the symbol table or dictionary, for example. Alternatively, the name of an expression
can be computed as a unique function of the operator and operands, independent of order, but this leads in general to many hard choices. If the expression a T b -t- c occurs,
followed by a + b, b -4- c, and a -4- c, a choice which loses some commonality must be
made.

as expressions or as flow control paths is machine and source language dependent. I n

not permit the change from the first to the second form. It is assumed that such decisions
are made prior to the CSX-M process.
Because with these algorithms the identities of expressions do not change, only expressions which are formally common are eligible for elimination. That is, in the following code:

value of d + c is available.
The algorithms attempt the elimination or motion only of expressions. Definition
points are considered to be fixed in their original places. Furthermore, code is moved only
"backward," never "forward."

3.2. BAsic ALGORITHMS. The idea of the method is this: The events of the program,
relative to a particular expression, are described by a set of Boolean equations--one for
each basic block (or equivalently, for each arc). These equations are solved, ~ giving for
each expression and for each block, the information as to whether the value of the expression is available (has been previously computed) at the entrance to the block. The program
itself can then be altered in an essentially trivial way to reflect this information.
At the heart of the entire method is the algorithm for efficiently solving the set of
Boolean equations. In order to simplify the notation, the description below is stated in
terms of a single formal expression (e.g. a ~ b). Because the pertinent information about
an expression at a point in the program is represented by one or two bits, it is possible to
solve the equations for many expressions at once, making use of the bit vector instructions in the repertoire of almost all computers. That is, each expression is assigned a particular bit in a bit string, and operations are carried out on the entire bit string at once.
For very large programs containing a large number of expressions, the size of the bit
string may be inconvenient for processing. In this case, it is possible to partition the
problem by expression to reduce the sizes of the bit strings at any one time.

can be extended to cover all cases, and to develop additional information about the expressions. For the simple case, the set of Boolean equations for a single expression is:

3.4. SAFETY--PROFITABILITY. Elimination of a common subexpression requires
alteration of only the block containing the expression. Code motion, on the other hand,
requires the alteration of at least two blocks: the block(s) originally containing the expression, and the block(s) to which the expression is moved. I t has been shown above how to
discover whether motion out of a block is possible; it has not yet been shown how to
discover if motion into a block is desirable. There are two factors to be considered: it is
profitable to move an expression into a block only if such motion makes possible elimination of the expression from some other block in a specified region, and it is safe to move
an expression into a block only if such motion can cause no side effects (e.g. divide check,
overflow) to occur that would not have occurred sooner or later in the original program.
Quite a few existing compilers ignore this safety constraint in moving code. For instructions which can cause no side effects (e.g. index add in many machines), the constraint does not apply. I n many programs instructions which could cause side effects in
fact do not; some way for the programmer to specify that this is the case would be desirable. Except to remark that the ability to respect the safety constraint in at least
some cases would seem to be necessary in a sophisticated optimizer, we will not attempt
to justify it. We will show how the present methods can be augmented to respect the constraint.

the value of an expression need be saved in a register or storage cell only where it is live.

I t is not surprising that profitability and liveness are so closely related: it is profitable
to insert a compute point into the region predecessor (s) only if the expression is then
live at the point(s) of insertion, considering only the blocks of the region. The profitability
value is in fact an approximation of the liveness value ws, on the trial assumption that

Blocks outside the region--and thus conditions on region exits--are not included in
the profitability determination because of frequency considerations. Regions are presumably chosen so that motion out of the region to a region predecessor decreases frequency of execution; whereas motion across a region--from a block to which there is a
path from a region exit to the region predecessor--is less likely to do so. A more sophisticated profitability analysis, which computed profitability as a numeric function of
execution frequencies, would presumably include a full live analysis. Of course, the problem of choosing regions and target blocks for motion then becomes an extremely difficult
one as well; note that the liveness determination depends on availability, which in turn is
computed with reference to a particular set of regions and target blocks.
This clarifies the relation between profitability and liveness, but we also need a way to
obtain an exact solution of the liveness equations for every block--approximate solutions
for only region predecessors, as for safety, are not good enough here. A very neat method
of completely solving successor-based equations (e.g. liveness and safety) has been shown
by Ken Kennedy in [4]. The essential idea is that the summary coefficients can be used
not only in forward substitution in outer regions, but also in backward (i.e. reverse predecessor order) substitution, to "skip over" the region. That is, once conditions on region
exits are known, the summary coefficients for the region can be used to immediately
translate these to region entry conditions; as one region entry is to the region head, this
also gives conditions at the start of all cycles in the region.
The method is to first obtain summary coefficients for all regions, using an inner to
outer forward substitution process, as we have been doing. Then employ an outer to
inner backward substitution process: For the outermost region, conditions on exits must
be known or assumed a priori; for inner regions, exit conditions are developed by processing each block of the next outer region (which contains the inner region, in summary
form, and all its immediate successors). As the blocks of a region are processed, safety or

step. Values are known for a successor not in the region or for the region head from
outer region processing (using summary coefficients, as explained), and for any other
block in the region from prior processing in the region (because processing is in reverse
predecessor order).
Of course, both the safety and liveness equations could alternatively be solved by a
backward substitution process similar to the previously discussed forward substitution
algorithms. However, regions with more than one exit probably occur in real programs
much more often than do multi-entry regions; K e n n e d y ' s method avoids the problems
that would thereby arise in pure backward substitution.
Kennedy outlines the solution process in terms of liveness of simple scalar variables,
which is simpler than the expression analysis because the value of a scalar variable is
always available after any reference (a definition point destroys the old value, but makes
a new value immediately available). To modify our equations for scalar variables, the

A "compute point" for a scalar variable is simply a use of it. The live analysis for variables would probably be done sometime after the CSX-M process, to include variables
arising during later optimization processes. The live analysis for expressions could also
be postponed, by merely marking compute points as redundant or nonredundant, then
treating these as uses and definition points of variables, respectively. The expression live
analysis, however, combines so neatly with the availability calculation, as we show in the
next section, that it seems a shame to put it off.

Summary

The paper has given solution methods for determining which instances of expressions in a
program can be deleted as common and which can be moved to presumably lower frequency blocks, for deciding which target blocks are eligible to receive moved expressions
(profitability) and whether motion into these blocks is safe, and for deciding where an
expression value must be preserved for later use (dead analysis). Various different options
have been shown, and opportunitl~s for approximate but simpler methods pointed out.
In this section we give in its entirety one of the algorithms outlined in pieces above.
The solution for CSX-M and profitability is developed in two passes over the basic
blocks and region summary blocks of the program: the first pass processes regions in
inner to outer order, and blocks in a region in predecessor order; the second pass processes
regions in outer to inner order, and blocks in a region in any order. The solution for liveness and the nonapproximate solution for safety are similar to this, except that here the
second pass processes the blocks of the region in reverse predecessor order. These two
orders are not incompatible, and, as we have derived the solution methods, all processes
share much common data. As this suggests, it is in fact possible to develop the CSX-M,
profitability, safety, and liveness solutions all together, in just two passes over the blocks
and summary blocks. The first pass--inner to outer, predecessor order--computes all
coefficients (C*, D*, D, ~, and 5:). The second pass--outer to inner, reverse predecessor
order--then uses these to obtain the final solutions. Except in one relatively minor case
(see the discussion of Figure 15, below), all values have been computed by the time they
are needed. The elegance of the entire method is rather satisfyingly demonstrated by the
combination of all processes into a single algorithm.

5. Evaluation
The author has not implemented the methods given here, so no actual performance
figures are included. I t seems clear t h a t the bit-vector processing itself would be quite
fast: with negligible exceptions, only two passes are made over each basic block and each
region summary block. The process does require initial construction of the bit vectors
from the code, association of definition points with expressions, and a final reflection of
derived information from the solution vectors back into the code. While these tasks are
not too expensive, it should be noted t h a t other less comprehensive b u t quite capable
methods exist, which can perform a complete C S X - M process and other optimizations
directly in one or two passes over the code itself~--that is, in probably little more time
t h a n is required to set up for the bit vector processing. All in all, however, the method
described herein is probably quite fast for one so powerful.
Space requirements, while appreciable, are not exorbitant. Space can be saved b y overlaying the solution vectors (x, z, and w) with the c, C*, and D* vectors; with a little extra

The method is clearly very powerful, in that it finds many cases not normally found by
an optimizer (see Figure 10, for example). Given the problem as defined by the equations,
the method can completely solve it (although see the discussion of Figure 15). Of course,
the equations do not exhaust the real world possibilities for optimization of the CSX-M
type; thus the method misses both the commonality and movability in a case like that in
Figure 17.
A weakness of the method is that it apparently does not combine easily with other
optimization processes. For example, constant or variable folding (Figure 17 shows an
example of variable folding), or reduction in strength (the replacement of a repeated
computation in a loop by a cheaper one--for example, replacing a z 2 + bx + c, where x
increases by a (region) constant for each iteration, by two additions). Strength reduction
is very important, and relatively expensive in compile time; thus it makes sense to find
commonality first, to avoid reducing the same expression in each of several different instances. However, strength reduction creates new initilization computations, which themselves may be movable or eliminable. This problem can be avoided by performing folding,
CSX-M, and strength reduction as a single process, but this is apparently not feasible
for the methods herein.
All in all, the method has an impressive elegance, which helps greatly in understanding
certain basic properties of programs. It is almost certainly more powerful than other
existing CSX-M processes (although it does not subsume them; see Figure 17). Further,
it is quite efficient enough to be used in production compilers. One probably would want to
use it only in a large, quite deluxe compiler, however: the simpler and (especially when
an entire optimizer is considered) probably more efficient methods referred to above are
quite capable enough for most compilers.
