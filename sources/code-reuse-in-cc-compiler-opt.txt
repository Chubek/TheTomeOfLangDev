This paper describes how the cmcc compiler reuses code both internally (reuse between different modules) and externally (reuse between versions for different target machines).
The key to reuse are the application frameworks developed
for global data-flow analysis, code generation, instruction
scheduling, and register allocation.
The code produced by cmcc is as good as the code produced by the native compilers for the MIPS and SPARC, although significantly less resources have been spent on cmcc
(overall, about 6 man years by 2.5 persons). cmcc is implemented in C++, which allowed for a compact expression of
the frameworks as class hierarchies. The results support the
claim that suitable frameworks facilitate reuse and thereby
significantly improve developer effectiveness.

The need to address the first two items is obvious, but
in production compilers, the third issue is important as
well. Given the complexities of current processors, no single heuristic produces consistently superior results. Consequently, compilers try multiple heuristics and pick the best
result. For example, the RS/6000 compiler [2] tries three
different register-allocation
heuristics, and then picks the allocation with the least spill code. The SGI MIPSpro compiler [29] uses 4 different scheduling strategies. Such an approach to structuring the compiler requires a high degree of
flexibility (i.e., the ability to modify some part of the compiler
while keeping the rest of the infrastructure unchanged). This
flexibility is even more crucial in an aggressive returgetable
compiler.
Various researchers and practitioners have embraced the
paradigm of object-oriented
design and implementation
to
achieve modularity and to increase code reuse [15, 281.
Generic class libraries for basic data structures such as linked
lists, stacks, queues, heaps, and so on, provide a first level of
code reuse [30, 261. Such basic data structures are pervasive
inside a compiler, and thus there is ample opportunity for
code reuse based on libraries within a compiler. However,
there exists a second level of code reuse based on patterns or
application frameworks [ 12, 3 1, 321. An application framework captures the control structure of a class of computations
but leaves specification of the exact functionality to the client
of the framework. For example, many optimization phases
consist of one or more data-flow analysis passes followed by
transformations based on the result of the analysis. Code can
then be reused by developing a single application framework
for global data flow. This framework factors out code that
is common among different phases, such as iterations over
the flow graph that modify the In and Out sets of each basic block. The framework is parameterized according to the
characteristics of the flow analysis (e.g., the direction, confluence operation, etc.); a client of the framework then provides
the details (e.g., in the form of a function to initialize the In
and Out sets).

Our goal for the cmcc compiler was to develop a competitive optimizing C compiler that is useful as a platform for architecture and compiler research. This goal implies the need
to support easy retargetting (to generate code for different
machines). Given the small number of people involved (the
authors), we strive for high internal (between modules) and
external (between versions for different targets) code reuse.
Our definition of code reuse is rather strict - we do not
permit any modification to reused code, since the compiler
supports multiple targets. If the reused code is included unchanged in all compilers, then all versions of the compiler can
benefit from advances or changes. This situation is different
from those environments
where “stand-alone” applications
are built: Two systems may start with the same class library
but then are permitted to change it according to their respective needs.
We note that there is no generally accepted definition of
reuse. Even changes of up to 25% of the source code have
been classified in the literature as reuse, with “slight revisions” [23]. Although such a form of reuse is better than
developing code from scratch, it nevertheless violates our requirement that reuse is based on complete, unchanged use of
the code base. In this paper, we report how application frameworks increase code reuse and ease compiler extensions (i.e.,
support the addition of new optimizations, different orderings
among transformations,
and new targets). Since we do not
allow any modification to the reused code, our experience
reported here makes a conservative statement about the reuse
through framework technology.
Other environments might
report even higher degrees of reuse if slight modifications are
allowed.

The cmcc compiler

We developed an optimizing,
retargetable compiler (the
Carnegie Mellon C Compiler or cmcc) for a complete programming language (ANSI C), with all the warts and subtleties that a real language implies.
Results for language
subsets (e.g., pointer-less languages) are difficult to extrapolate to other compilers.
cmcc is coded in C++ and produces
assembly language for a variety of target machine architectures. It uses the ICC ANSI C front end [lo]. Table 1 lists
the global optimizations performed by cmcc.
The global register allocator integrates live range splitting [24] with a graph-coloring register allocator [6]. Register
allocation is done as part of code generation (although it is
listed here as an optimization, it is not part of the global optimizer).

The global optimizer’s interface to cmcc’s code generator
is encapsulated inside an abstract code generation class (this
is an example of an inre@zce class [3 11). Each target’s code
generator inherits from this class. The register allocator and
instruction scheduler are machine independent and operate
on schedules of abstract instructions.
To test our claims of
retargetability, we chose two extremes of the range of possible
target machines. cmcc currently generates code for various
RISC machines (MIPS, SPARC, DLX) and an experimental
LIW machine (Intel iwarp).

Description

Informally, a DFA problem is defined by several parameters
(see the appendix for a more detailed description):
Direction The direction of a DFA can be either forward or
backward. Examples of forward analyses include available expressions and reaching definitions. Example of
backward analyses include anticipated expressions and
live variables.
Confluence The confluence operation can be either the conjunction or disjunction operator, resulting in either an
all paths or any paths problem respectively. Available
expressions and busy expressions are all paths problems, while reaching definitions and live variables are
any paths problems.
Initial In and OZL~sets The initial value of the In (Out) bit
vector at the source (sink) node in the control-flow graph
depends on the data-flow problem. For instance in live
variables, global variables are considered live at the sink
node and local variables are not live, while in available
expressions all expressions are considered not available
at the source node. The initial values of the In and Out
bit vectors at all other nodes depend on the confluence
operator.
Gen and Kill sets The Gen and Kill

Transfer functions The transfer functions relate the In and
Out sets at each node in the control-flow graph. The
most common transfer functions are Out = (In Kill) + Gen for forward flow problems and In =
(Out - Kill) + Gen for backward flow problems.
To solve a DFA problem, the transfer functions are repeatedly
solved at each node in the control-flow graph until a fixed
point is reached. To speed up this computation for forward
flow problems, the transfer functions can be solved in reverse
post order of the control-flow graph. To speed up the solution
for backward flow problems, the blocks can be visited in the
reverse order of the forward flow case.

In the cmcc compiler, code scheduling is a separate code
generator phase that takes and produces schedules of instructions. Like the other code generation phases, scheduling operates on the Ins t class, and is thus machine independent. The
purpose of scheduling is to reorder instructions such that the
target machines’ resources are used more effectively. Therefore, the scheduler must accurately model the result latencies
and resource requirements of each instruction, while still being machine independent. Moreover, for multiple-issue (i.e.,
superscalar and VLIW) machines, the scheduler must accurately model the instruction fetch and decode constraints
of the target machine. For a VLIW machine, the scheduler
packs instructions (since each instruction contains multiple
operations), while for a superscalar machine, the scheduler
schedules instructions into an instruction window that models
the instructions that are fetched and decoded as a unit by the
processor at runtime (the size of the window is determined

Note that this scheduling framework almost completely
covers the range of possible local list schedulers.

List scheduling is the basic local scheduling technique used
in cmcc (and many other compilers); it consists of four steps:
(1) initializing a ready list that holds all instructions that are
ready to be scheduled (ready instructions),
(2) choosing a
ready instruction I based on a candidate selection heuristic,
(3) inserting I into the schedule after making sure the resource
constraints of 1 are satisfied, and (4) adding into the ready list
those instructions whose precedence constraints are satisfied
by the scheduling of I.
The direction of code scheduling is determined by the order
in which instructions are considered (i.e., placed on the ready
list). If instructions are placed on the ready list after their
descendants are scheduled, the code scheduler is a forward
scheduler. In this case, the scheduler starts with the producers
of values. If instructions are place on the ready list after their
parents are scheduled, the scheduler works backward; that is,
it starts with the consumers of values.
The manner in which candidate instructions are selected
and inserted into the schedule in steps 2 and 3 of the list
scheduling algorithm can be either instruction oriented or
cycle oriented.
An instruction-oriented
scheduler chooses
a ready instruction (using the candidate selection heuristic),
inserts the instruction into a schedule slot such that the precedence and resource constraints are satisfied, and then modifies the ready list. A cycle-oriented scheduler steps through
the schedule cycle-by-cycle.
For each cycle, it chooses a
ready instruction whose precedence and resource constraints
are satisfied in the current cycle (using a candidate selection
heuristic to break ties if there is more than one such instruction), inserts the instruction into the schedule, and then modifies the ready list.

Most compilers maintain a separate executable for each new
target. This creates problems for version management and
validation, as each target’s compiler executable must be built
and maintained separately. We avoid this problem by having
a fat compiler, a single compiler executable that can generate code for any target. This can be done by dynamically
selecting one of several implementations
of a code generation interface, a strategy that has also been used explicitly by
other projects[ IO], but that falls out of our frameworks-based
implementation
for free.
The class system for global data-flow analysis stabilized
after the second revision. We are now at the third iteration
of the code generator. Readers should not be discouraged by
the number of iterations. Each iteration reduced the amount
of code, a step we consider to be important for the long term.
Also we fought at the same time with different C++ compilers. In the process of moving from one compiler to another,
on a variety of platforms, we encountered more than one unpleasant surprise. (We used, with different success, g++ on
Suns and Alphas, the DEC Alpha C++ compiler, SGI’s C++

Conclusions

The low-level objects to be used by an optimizing compiler
are well understood - the usual data structures from an advanced undergraduate algorithms class go a long way, and
there exist a number of class libraries for common data structures. However, the design of frameworks for global dataflow analysis, instruction scheduling, and register allocation
as well as the set of abstract classes that form the foundation for the code generator, allow us to reuse code beyond
low-level building blocks.
These frameworks contribute significantly to the organization of the compiler code. The code is clean and concise,
easy to understand, and has been reused a large number of
times: the code for the data-flow module has been reused 15
times, the code generator code is reused 3 times, and more
than 75% of the code for a code generator is actually part of
the common code base. The domain of optimizing compilers provides a further example for the power of the idea of
application frameworks.
The abstract classes of the code generator play a crucial
role in our plan to build a retargetable system, but their importance extends this aspect. These abstract classes allow us
to make the compiler extensible. The code selector, register
allocator, instruction scheduler, and code emitter are written
