ABSTRACT

1.

Detecting and characterizing the effects of software changes is a
fundamental component of software maintenance. Version differencing information can be used to perform version merging, infer
change characteristics, produce program documentation, and guide
program re-validation. Existing techniques for characterizing code
changes, however, are imprecise leading to unnecessary maintenance efforts.
In this paper, we introduce a novel extension and application of
symbolic execution techniques that computes a precise behavioral
characterization of a program change. This technique, which we
call differential symbolic execution (DSE), exploits the fact that
program versions are largely similar to reduce cost and improve
the quality of analysis results. We define the foundational concepts
of DSE, describe cost-effective tool support for DSE, and illustrate
its potential benefit through an exploratory study that considers version histories of two Java code bases.

Detecting and characterizing the effects of software changes is a
fundamental component of software maintenance. Version differencing information can be used to perform version merging, infer
change characteristics, produce program documentation, and guide
program re-validation. For example, during regression testing, differences can be used to focus re-testing efforts by selecting only
test cases that exercise the modified sections of code. Reducing the
scope of maintenance activities by exploiting version difference information, can significantly reduce maintenance costs.
Computing version differences involves comparing two programs by systematically matching representations. Differences can
be computed on a variety of representations (e.g., flow graphs [17],
abstract syntax trees [2], lines in program source files [9]) of program versions. Calculating a source file diff is the most common
approach used in practice and while it is automated and efficient,
it is very imprecise. Formatting or minor syntactic changes to a
program, that do not alter its meaning, can cause a diff to indicate version differences. Subsequent maintenance activities that
use source differences as their starting point to identify the effects
of a change may, consequently, do large amounts of unnecessary
work. We believe that recent advances in behavioral program analysis techniques, more specifically those associated with symbolic
execution [14], make it possible to produce significantly more precise version differencing information.
In this paper, we present a novel technique, differential symbolic
execution (DSE), that combines state-of-the-art symbolic execution approaches with a new over-approximating symbolic execution
technique to characterize the effects of a set of program changes in
terms of behavioral program differences. DSE supports multiple
forms of equivalence checking, and is capable of precisely characterizing behavioral program differences when equivalence cannot be shown. Moreover, our formulation of DSE allows it to
“skip” the symbolic execution of the parts of a program that are
unchanged between versions. This has the potential to significantly
reduce analysis cost and to avoid some of the fundamental limitations of symbolic execution. Finally, DSE supports a wide range
of program evolution tasks including the problems of equivalence
checking and regression test generation.
The contributions of our work lie primarily in the development of
a methodology for performing DSE and the foundational concepts
that enable DSE to leverage advances in symbolic execution to
precisely characterize the changes between two program versions.
Specifically, our work: (1) develops a methodology for precisely
characterizing behavioral program differences using symbolic execution, (2) develops techniques to compute over-approximating
symbolic method summaries by identifying and automatically summarizing the behavior of common program fragments, (3) defines

OVERVIEW

In this section, we provide an overview of the methodology for
performing differential symbolic execution and illustrate its application to a small example. We begin with a brief explanation of
symbolic execution.

2.1

Our Approach

The DSE methodology performs a form of differential program
analysis [15, 29] that leverages advances in symbolic execution [1,
11, 16, 27, 28] to precisely characterize the behavior of one program version relative to another. This analysis is capable of (a)
demonstrating that the two versions are equivalent, or, if they are
not, of (b) characterizing the behavioral differences between versions by identifying the sets of inputs that cause a different effect.
We illustrate the principles and several applications of our analyses
here.
Figure 1 illustrates the steps involved in performing our analysis. In its simplest form, DSE consists of 3 steps. First, it takes
two versions of a method, Vi and Vj , and symbolically executes
each method version to generate symbolic summaries. Second, it
checks whether the summaries are equivalent. As we explain in
Section 4, we define functional equivalence, i.e., the versions have
the same black-box behavior, and partition-effects equivalence, i.e.,
the versions have corresponding sets of paths through their implementations. These notions of equivalences are useful for different
applications, and each is checked by encoding summaries as a series of validity queries to an automated decision procedure, e.g.,
CVC3 [7]. The third step involves generation of a behavioral delta
by DSE, denoted ∆, if the summaries are not equivalent. The delta
precisely characterizes the input values on which the versions exhibit different behaviors.

There are a wealth of potential client applications for DSE.
Consider version 2 of logicalValue(), which is the result
of applying three of Fowler’s code refactorings [10] to version

they can give rise to significant textual and syntactic differences
in the program. For instance, applying the standard diff tool

determines the two versions to be equivalent which provides assurance that refactorings have been applied correctly; experience
has shown that producing correct refactorings can be difficult when
performed manually or when using tool support [8].
Client analysis such as impact analysis [19] and regression test
selection [20] could also leverage DSE’s more precise deltas to reduce the impact set size or the number of tests selected for execution. Moreover, the partition-effects equivalence of versions 1 and
2 of logicalValue() indicates that any test used on version
1 provides equivalent coverage on version 2. Consequently, the
refactoring neither invalidates existing tests nor calls for new tests
to achieve a desired coverage goal.

3.

Symbolic Program State

Symbolic execution calculates values for program variables as
expressions defined over constants and symbolic variables using a
given set of operators. A symbolic variable denotes an unspecified typed value; in this work we denote symbolic variables with
capital letters. During symbolic execution, symbolic variables are
introduced whenever an unspecified value flows into a method,
e.g., through parameters. For example, T in Section 2.2 denotes
the symbolic value of parameter t on entry to a call of method
logicalValue() in Figure 2. We associate symbolic variables
with memory locations that are written to, but are not local to a
method, e.g., side-effected globals or the return value of a method.
For example, RETURN in Section 2.2 denotes the symbolic return
value of method logicalValue() in Figure 2. We refer to the
set of locations written to (or read by) a method, m, called on arguments ~a, as Write(m, ~a); Write(m) denotes the locations that may
be written on any call.
The state of a symbolic execution is defined as (l, pc, ~v ) where l,
the current location, records the next statement to be executed, pc,
the path condition, is the conjunction of branch conditions encoded
as constraints along the current execution path, and ~v , the symbolic
value store, is a vector of symbolic expressions representing the
current values of memory locations, where v[j] is the value at location j. For simplicity we assume that memory locations can be
indexed and we define a symbolic value store update, ~v hd, si, to be

check the satisfiability of the updated path conditions and, when
a path condition is found to be unsatisfiable, symbolic execution
along that path halts. Decision procedures for a range of theories that underly constraint languages, such as, linear arithmetic,
arrays, and equality over uninterpreted functions, are readily available, e.g., CVC3 [7]. While these procedures can form an effective basis for symbolic execution of non-trivial programs, there are
many data types and operations that require theories for which costeffective decision procedures are not currently available e.g., nonlinear arithmetic (this is one of the reasons we use abstract summaries as described later in this section).

SUMMARIZING PROGRAM BEHAVIOR

We represent the behavior of a program (or a part of a program)
using a symbolic summary. Conceptually, a symbolic summary
captures a set of distinct cases of a program’s behavior, where each
case is characterized in terms of a set of input values and the corresponding set of effects on program variables. The presence of
loops, recursion, complex arithmetic expressions, and other program structures for which sophisticated theories are necessary in
order to reason about program behavior may result in symbolic
summaries that vary in (a) precision – one summary is more precise
than another if it represents less infeasible behavior (i.e., the summary includes fewer infeasible paths), and (b) completeness – one
summary is more complete than another if it represents more feasible behavior (i.e., it characterizes program behavior over a larger

Scalability is a key concern in symbolic execution, especially in

summary defines “what” a method computes by pairing descriptions of input values with the changes to the program state effected
by executing the method on those values.
The basic building block of a symbolic summary is the constraint. Each constraint defines either the set of concrete values for
method inputs, or the set of effects, e.g., return values caused by
method execution. Constraints consist of conjunctions of boolean
expressions defined in the constraint language, and are combined
to form a partition-effects pair.

3.3

Incomplete Summaries

Unfortunately, it is not always possible to calculate a complete
summary using symbolic execution. There are two main obstacles:
(1) cost-effective automated decision procedures may be unavailable for theories needed to model certain program structures (e.g.,
non-linear arithmetic) and (2) loops and recursive method invocations, in general, are impossible to bound using input constraints.
The inability to reason about these structures results in summaries
that are incomplete with respect to reasoning about a method’s input space; the loop-iteration bounded summaries in Section 2 illustrate this problem.
The completeness of a summary is based on the degree to which
the input partitions in the summary cover the method’s input space.

3.4

Abstract Summaries

Symbolic summaries are as precise as the underlying theories
implemented by the decision procedures used. It is possible to
define less precise symbolic summaries, but researchers applying
symbolic execution to testing have not found value in this approach
since they rely on symbolic execution for exploring only feasible
paths, forming an under-approximation of program behavior. In
this section, we develop an over-approximating symbolic summary,
that may include infeasible paths, but is useful in differential symbolic execution.
An abstract symbolic summary captures the fact that a method
(or block of code) may partition its input space, and within each
partition it produces effects on program locations; in other words,
it abstracts the number of partitions and the specific nature of each
partition and its associated effects.

Partition-effects Equivalence and Delta

If one wishes to reason about the path-equivalence of two versions of a method to, for example, infer coverage properties of an
existing test suite on the new version, then functional equivalence
is inadequate. Partition-effects equivalence, on the other hand, considers both “what” a method does and “how” it partitions the input
space, therefore partition-effects equivalence considers the equivalence of each method’s input partition independently.

EQUIVALENCES AND DELTAS

In this section, we define two notions of equivalence between
methods (or code blocks) based on summaries. Functional equivalence relates methods that have the same externally observable behavior, whereas the finer-grained notion of partition-effects equivalence takes into account the way that a method’s implementation
partitions its input space. Associated with each type of equivalence
is a corresponding notion of delta which captures the behavioral
differences between methods symbolically.
For the most part, our definitions are insensitive to the use of
symbolic or abstract summaries. In practice, as we discuss in Section 5, we use abstract summaries in DSE to capture the behavior of
the portions of a program that are unchanged between versions, and
symbolic summaries for changed portions. Given this, summaries
will, in general, have constraints built by composing both symbolic

Tool Support

We have adapted the Java PathFinder (JPF) analysis toolset’s recently developed symbolic execution framework [16] to implement
support for DSE. Java PathFinder is an open source tool that acts as
a customized Virtual Machine, operating on Java class files. Symbolic execution in JPF v4.1 currently supports mixed symbolic and
concrete execution of integer and real data types. Symbolic execution is performed based on user specification of methods, parameters and globals to be treated symbolically. JPF traverses interprocedural paths during symbolic execution, accumulating symbolic constraints which are output for method summaries by a customized listener in the symbolic execution framework.
The JPF symbolic execution framework is implemented as an extension of JPF (the symbc JPF extension). It includes a customized
bytecode instruction factory that replaces or extends the standard
concrete execution semantics with symbolic execution. Symbolic
information is stored in attributes associated with program data.
JPF uses the Choco constraint programming system [5] for decision
procedure support and constraint solving. Because state matching
is, in general, undecidable when states represent path conditions on
un-bounded data, JPF does not perform state matching on symbolic
values. Loops and recursion can be bound by placing a depth limit
on JPF’s search depth or by limiting the number of constraints encoded for any given path; JPF indicates when one of these bounds
has been reached during symbolic execution.
To perform equivalence checking and generate deltas we have
developed a prototype tool that reads method summaries compiled
by the customized JPF symbolic execution listener and generates
inputs to CVC3. The CVC3 inputs encode completeness, equivalence and the individual checks required to calculate partitioneffects deltas. CVC3 supports validity and satisfiability queries
over logical formulae expressed in terms of a rich set of base types,
that includes uninterpreted functions, as well as user defined types.
The conversion of DSE summaries to CVC3 input is essentially a
transliteration of syntax.
For partition-effects equivalence and delta calculations, we expand the pairs of partition-effects pairs from the two summaries being related into separate CVC3 queries and then combine the query
results. Since summaries are always finite sets, calculating validity
of the quantified formula in definitions 4.4 and 4.5 is sound.
Combining JPF’s existing symbolic execution support with our
prototype DSE tools realizes intra-procedural DSE. We have also
developed partial support for abstract compositional DSE, however,
it does not support some features of the Java language, e.g., exceptional returns from abstractly summarized methods. We also
include only limited support for arrays and data structures. In the
future, we plan to explore ways to handle exceptional behaviors in
abstract summaries, and to incorporate support for input arrays and
data structures, using the lazy initialization approach from [27].

Applicability and Completeness of DSE

We provide a characterization of the changed methods in JMeter
and Siena to assess the applicability of DSE and the potential effectiveness of abstract summaries in providing more complete differential analysis in the context of real-world applications.
JMeter had 352 methods changed between versions 1 and 2.
Of these changes, 80 correspond to new methods, 8 are deleted
methods, 6 are methods with signature changes, and 163 are nonfunctional changes such as pretty printing or changes related to
comments. Inspection of the remaining 95 methods containing
functional changes revealed that 68 can be analyzed with DSE to
either determine equivalence or describe version differences. Our
assessment was conservative in that we counted only methods for
which full support is currently available in DSE. For example,
methods with exception handling code are not counted even though
those features could be handled in future versions of our tools.
Of the 68 methods analyzed by DSE, 2 contain a loop in the
common code between versions, 4 contain calls to methods which
are unchanged and contain a loop, and and 11 call library methods which may contain significant complexity. Applying standard
symbolic execution to such methods, would generate incomplete
summaries. With abstract summaries, however, those 17 methods
can be completely analyzed.
In the first five versions of Siena, we saw fewer modifications
but a similar trend. There were 28 changed methods, 11 were
new methods, 10 were formatting changes, and 7 involved actual
code changes. Of those 7 changed methods, 3 can be summarized
completely with standard symbolic execution, and another 2 can be
summarized completely when abstract summaries are used.
Although our assessment regarding the applicability of DSE is
limited to a small number of artifacts, the results are encouraging
and illustrate the potential of DSE and the use of abstract summaries to exploit the differential nature of multi-version analysis to
scale to real code.

In the context of test suite evolution, Apiwattanapong et al. [3]

identifies program statements in a dependency graph within a specified distance from a change, applies symbolic evaluation to capture the potential program states at the identified statements, and
produces test requirements based on a pairwise comparison of the

than program states, which avoids the imprecision that comes with

which the analysis completely covers program behavior and when

RELATED WORK

The problem of differencing programs has been widely studied.
Tools that difference various representations of programs source
code [2, 9, 17] are used everyday by practitioners to detect changed
source files when using CM systems and to construct software
patches. These tools also are used as the first-phase in more indepth analyses of program differences and the impact that a change
may have on other parts of the program. Using source difference as
a starting point, multiple researchers have investigated approaches
that identify an approximate characterization of the source code
whose execution behavior may differ as a result of the change, e.g.,
[19, 20]. While useful, these techniques suffer from imprecision
which can cause large parts of a program to be identified as potentially different. Our work focuses on developing more precise
characterizations of program differences that offer the potential to
reduce the cost of software maintenance activities.
In recent years, researchers, e.g., [15, 29], have begun to consider the challenges and opportunities that lie in targeting program
analysis to version histories. Notkin identified several advantages
of what he terms longitudinal program analysis. For example, program analysis cost can be amortized across multiple versions by
reusing analysis results, analyses can target version differences, and
analyses that might otherwise be intractable may become tractable
when they focus on closely related program versions. We believe
that DSE is the first instance of a longitudinal analysis framework
that realizes all of these benefits.
DSE’s approach to compare program versions was in part inspired by the work of Siegel et al. [22] who apply a combination
of model checking and symbolic execution customized for floating point calculations, to verify the equivalence of sequential and
parallel versions of a program solving a numerical computation.
Their notion of equivalence is tunable, but it always captures the
essential idea that the computed results are the same for the parallel
and sequential programs for all inputs. In Siegel et al.’s work the
exploration of concurrent process schedules is crucial to judging
the equivalence of a sequential program run with the corresponding set of possible parallel program runs. While we implemented
DSE in the JPF model checking framework to take advantage of its
rich and flexible analysis infra-structure, our main objective was
not to explore thread schedules. Instead, DSE provides a more

CONCLUSIONS

We have introduced differential symbolic execution as an approach for precisely calculating behavioral differences between
versions of program methods. At the core of DSE are notions of
method equivalence and deltas. We define equivalences and deltas
that are sensitive only to black-box behavior and that consider a
measure of white-box behavior. Variants of these equivalences accommodate the kinds of imprecision that commonly arise when
performing symbolic execution of real Java software systems.
Building on the foundational DSE concepts, we present three
classes of alternative formulations of DSE and describe tool support
for two of those approaches. We illustrate the application of those
tools to reason about selected changes from program version histo-

236

ries. For each such change, we describe a potential client analysis
that leverages DSE results to support the evolution of test suites, to
provide assurance that refactorings do not change program behavior, and to characterize the nature of a version change.
This work is the first step in focusing the recent significant advances in symbolic execution on problems of software evolution.
Our future work will further develop DSE algorithms, engineer
scalable implementations of those algorithms, develop automated
support for DSE client applications, and then study the cost and
effectiveness of DSE in automating software maintenance tasks.
